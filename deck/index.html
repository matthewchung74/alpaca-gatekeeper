01 · thesis

Where the risk limits live

The common approach is to write the risk rules into the system prompt — never risk more than X — and rely on the model to follow them.

A model asked to respect a position limit will respect it most of the time. We wanted the limits to hold the rest of the time too.

So the system is split in two. Claude decides what to trade. Deterministic Python decides whether that trade is allowed to exist. They are separate processes, and the model has no access to the second one.

The model never states a dollar figure. It proposes strikes and a quantity, and the risk layer derives max loss from the contract specs, then resizes the position to fit the budget.

Nothing the model outputs can raise a limit, skip a gate, or size a position up. It runs unattended on Google Cloud: four entry cycles a day, exit sweeps every ten minutes.

03 · the options path

What it trades

StructureVertical credit spreads. Sell the strike nearer the money, buy the strike beyond it.
Why the long legIt caps the loss. Max loss is a known number before the order is submitted rather than an open-ended exposure.
Expiry2026-09-03 only — everything settles the day before the deadline.
Strike selectionThe model only sees contracts between 0.05 and 0.35 delta. A gate then enforces 0.20–0.35 on the short leg.
Profit targetClose at 50% of the credit captured.
StopClose when the cost to close reaches 3× the credit taken.
Expiry dayFlatten 30 minutes before the close — an assigned short strike would leave stock in the account on submission morning.

A convex “satellite” sleeve that buys defined-risk direction is implemented alongside the core. Across this event the regime never permitted it, so every trade shown here is core premium selling.

04 · regime

Regime sets direction and size

RegimeRisk budgetRights permittedRationale
sideways12.00%P and Crange-bound tape is the best case for short premium
bull10.20%P onlynever sell calls into a trend that is running
bear4.20%C onlydowntrend: no short puts, size cut hard

A bear read cuts the core budget from 12% of equity to 4.2%, a 35% multiplier applied by code before any gate runs. The model is not given that number and cannot set it.

05 · alpaca integration

How it talks to Alpaca

Every order leaves through the Alpaca CLI. It gives structured JSON in and out, exit codes, automatic retry on 429 and 5xx, and --client-order-id for idempotency.

alpaca cli
alpaca data option chain --underlying-symbol SPY --expiration-date 2026-09-03
alpaca data bars · latest-quote · news · calendar · clock
alpaca account get · position list
alpaca order get · order cancel

# order submit does not expose the multi-leg flags,
# so spreads go through the raw Trading API:
alpaca api POST /v2/orders   order_class: mleg

Chains, bars, quotes, news and the trading calendar all arrive through the CLI. Account state and positions too. Multi-leg orders are the one case that needs the raw endpoint.

06 · what the live API taught us

limit_price on a multi-leg order is a signed net price.

Negative means a credit you require. Positive means a debit you will pay. Sending +0.80 on a credit spread reads as “I’ll pay up to 0.80” — which any credit trivially satisfies, so the limit never binds and the order fills at whatever the market gives.

Test against the live APISpread worthResult
demanded +2.501.23filled at 1.22 — limit never bound
demanded −2.501.23correctly rested unfilled

We found this by testing against the live API rather than reading the docs. Fixing it also made two previously dead code paths live, since orders can now rest unfilled or fill partially, and that surfaced three further bugs.

● account_guard refuses to trade the judged account outside the competition window. It raises an exception rather than a warning, because the eligibility of the whole submission depends on there being no fills outside that window.

● delta_band was added mid-event. The prompt had asked for a 0.25–0.30 short delta since day one, but no gate checked it, so a 0.304-delta call passed. Each gate is a pure function of the proposal plus observed account and market state.

09 · a rejection

A cycle that was blocked

2026-09-01 · 12:32 ET
proposal: IWM 2026-09-03 C 293.0/296.0 x16 @ 0.45

[BLOCK] liquidity   long leg IWM260903C00296000
            spread 11.8% > 10% of mid

The model proposed IWM four separate times and was rejected each time on bid-ask width. On the fifth attempt it proposed a narrower spread, 293/295 instead of 293/296, and the tighter structure cleared the gate.

The liquidity gate also protects the credibility of the P&L. Paper trading can fill wide, illiquid contracts at prices a real book would not get, so the gate keeps the results closer to what the strategy would actually have achieved.

10 · what runs while nobody watches

A fill that arrived after the code stopped waiting

An order filled 78 seconds after submission. The code polling for that fill stopped at 16, so the journal recorded it as unfilled while the broker held a 20-lot spread. Exit management reads the journal rather than the broker, so no profit target, stop or expiry flatten applied to it.

CauseFixing the signed limit turned instant fills into resting orders. The 16-second poll had been set when fills were instant, and its result could not distinguish an order the market declined from one still working.
The fixCancel on timeout, re-poll, and journal the price that actually filled. A close that does not fully fill no longer marks the spread closed.
The netA monitor reconciles broker positions against the journal every 15 minutes and escalates when they disagree.

The monitor caught the next failure within minutes: a stop whose limit was capped at the stop level, which could not fill once the position moved past it.
